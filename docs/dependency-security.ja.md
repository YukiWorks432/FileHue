# 依存の更新と監査

通常の第三者依存は公開から7日（168時間）経過した版を取り込む。直接依存、推移的依存、ビルド依存、試験用依存も対象とする。待機は公開直後の問題が発覚する時間を確保するためであり、経過した版の安全性を保証しない。

## ビルド前の確認

Cargo.lockを正本とし、通常のビルド・試験では`--locked`を維持する。監査ツールは信頼した環境で`cargo install cargo-deny --version 0.20.2 --locked`により事前導入する。導入するツール自身とそのロック依存も信頼の起点になる。更新候補のクレートをコンパイルする前に次を実行する。

```powershell
just audit
```

justから導入済みのcargo-denyを直接呼び、全体の監査、Windows x64へ絞った監査を順に行う。事前に補助処理が例外の期限と対象版を検証し、標準の検査設定へ有効な例外を追加した一時設定を作る。xtaskや製品はビルドしない。

対象版はcargo metadataで得た同名クレートの全版と照合する。承認版が残っていても未承認版が共存すれば失敗する。metadataは依存を取得し得るがコンパイルしない。期限はUTCの日付の開始時点で失効する。全体では未使用の例外をエラーとし、Windowsだけで未使用になる他OS用の例外は警告として残す。

候補のビルドスクリプトと手続きマクロはコンパイル中に実行される。監査後のビルド・試験にも公開トークンや署名鍵を渡さない。`--offline`やcargo-denyは実行環境を隔離する機能ではない。公開後は使い捨てのCI環境で検証し、署名・公開ジョブと権限を分ける。信頼できないPRに開発PCの認証情報を渡さない。

## 判定と個別例外

[deny.toml](../deny.toml)はcargo-denyの標準設定であり、脆弱性・依存元・ビルドスクリプトの検査を定める。例外の指摘ID・理由・正確な対象版・依存経路・確認日・再確認期限は[advisory-exceptions.json](../security/advisory-exceptions.json)だけに記載し、deny.tomlや本文に一覧を複製しない。新しい脆弱性、経路変更、上流の対応版が出た場合は期限前でも見直す。

補助処理は例外を検証してから、cargo-deny標準の`advisories.ignore`へIDと理由を渡す。設定の生成失敗や例外の不正・重複・期限切れ・対象版の不一致では監査へ進まない。生成先はGit管理外の`work/dependency-audit/`で、実行ごとに別のファイルを作り、既存ファイルを上書きしない。deny.toml自体には例外がないため、cargo-denyを直接呼んでも期限・対象版が未検証の例外は適用されない。

cargo-denyの未指定の検査を一括実行すると権利条件の別判定が混ざるため、入口では`advisories bans sources`を指定する。ライセンスの選択・原文・提供ソースは既存のcargo-aboutと[配布手順](distribution.ja.md)で管理する。

| 指摘 | 判定 |
| --- | --- |
| 既知の脆弱性・健全性の問題 | 原則停止。対象APIを使わない場合も経路と影響を個別確認する |
| 取り下げられた版 | 原則停止。必要なら理由と期限を伴う個別の判断を先に行う |
| 未許可の依存元 | 停止。原則crates.ioを使い、Git依存は個別許可とコミット固定を必要とする |
| 保守停止 | 個別の経路・版・影響・見直し期限を確認して例外とする。種類全体を無視しない |
| 同一クレートの複数版 | 警告。依存グラフ上で必要な重複を一律に禁止しない |
| 原文や提供ソースの不足 | 権利確認の未完了として配布の判断へ残す |

監査は更新時、PR、公開候補の確定前に行う。公開後は毎日、依存を変更していない場合も最新の指摘を確認する。データベースの取得失敗を成功扱いしない。オフライン検査のデータベース許容期間は1日であり、オンラインでの取得成功の代用にはしない。対象コミット、Cargo.lockのハッシュ、ツール版、監査DBのコミット・取得時点、終了コードをPRの検証結果へ記録する。詳細なログ・公開日時の照会結果・一時設定はwork/またはCIの成果物へ保存し、監査のたびにGitへ追加しない。DBの場所は`CARGO_HOME/advisory-dbs`を確認し、各チェックアウトで`git rev-parse HEAD`を使う。

補助処理は[prepare-dependency-audit.ps1](../scripts/prepare-dependency-audit.ps1)へ限定する。監査前に同じワークスペースの依存をビルドしないため、この処理だけはPowerShellで実行する。契約試験は既存のRust製xtaskに置き、監査成功後に`just test-policy`または`just verify`で確認する。生成設定を独立したTOMLパーサーで読み、理由の引用符・改行・Unicodeが保たれることも検証する。

## ビルド時に実行される依存

`bans.build.allow-build-scripts`は現在の外部クレートの名前と版へ限定する。初期一覧は既存のCargo.lockと各パッケージのターゲットから作った信頼基点であり、全依存のコード監査を完了した記録ではない。Windowsだけでなく他OS用の既存ビルドスクリプトも記録する。

新規の名前・版を追加する場合は、build.rs、呼び出す補助コードとコマンド、生成ファイル、通信の有無、追加されたビルド依存・手続きマクロを確認する。一覧を依存更新に合わせて無条件に自動生成し直さない。許可済みの版でも、すべての悪意ある動作を検出する保証はない。補助スクリプトやネイティブ実行形式の検出は警告を保持するが、同梱されただけで実行されたとは判断しない。

## 手動で更新する

1. 変更のない基点と監査結果を記録する。`cargo update --dry-run`で互換範囲内の候補を確認する。これは依存をコンパイルせず、Cargo.lockも保存しない。
2. crates.ioの対象名・版の公式APIから公開日時を確認する。最新が7日未満なら、互換範囲の中間版も調べる。日時不明、未来の日時、7日未満は通常更新で採用しない。問い合わせへ非公開URL・個人パス・認証情報を含めない。
3. `cargo update -p <名前> --precise <確認した版>`で選び、Cargo.lockに追加・変更された推移的依存もすべて同じ条件で確認する。想定外の若い版が入れば、ビルドせず更新内容を見直す。元から固定されていた版が若いことと、新しく採用する版の判断は区別する。
4. 新しいビルドスクリプトの許可、依存元、既知の指摘、権利表示を確認する。検査ツールを含め、候補依存で先にビルドしない。
5. `just audit`、`just verify`、`just licenses`、完成ZIPの検証を実行する。GUIへ影響する依存変更はGPUIのtest-supportと描画画像でも確認する。設定・文書だけの変更なら画像を省略する理由を記録する。

公開日時の照会例は`https://crates.io/api/v1/crates/<名前>/<版>`である。`version.created_at`をUTCとして確認し、基準時刻と一緒に証跡へ残す。更新候補がない場合は待機を緩めず、確認結果と再確認日をIssueへ残す。GPUI Kitの固定版や大きなAPI移行は通常のロック更新と分ける。

既知の脆弱性の修正版は7日待機を短縮できる。ただし名前・正確な版・指摘ID・変更内容・短縮理由・確認者をPRへ記録し、通常の監査と試験は省略しない。恒久的な名前空間単位の除外は作らない。

7日待機は手動更新の採用条件と公開後の更新提案に適用する。just auditが全依存の公開日時を取得して判定するものではない。個別の更新結果や保留理由はIssue・PRへ記録し、恒久的な運用文書へ日時付きの監査記録を追加しない。

### パック取得時の証明書検証

パック取得にはreqwestとrustlsを使い、暗号処理はring、信頼するルート証明書はwebpki-rootsから明示的に構成する。OSの証明書ストアへ自動的に切り替えない。証明書の連鎖・有効期間・接続先名の検証を無効にせず、HTTPS限定・転送先の許可一覧・取得上限を維持する。reqwestの既定値が変わる更新でも、この構成を引き継ぐ。

認証局の秘密鍵漏洩では、検証ライブラリによる拒否とルート証明書集の更新を併せて確認する。該当する修正版は上記の個別判断で待機を短縮し、関係のないTLS依存まで一括で除外しない。OSでの失効確認や通信先が現在安全であることまで保証するものではない。

## 公開後の導入

公開後の自動更新提案の方式は未決定とし、Dependabotを候補として検討する。選定時には、通常更新は週1回・公開から7日待機・日時不明は保留・自動マージなしという条件を維持する。推移的依存の扱いと、既知の脆弱性への更新提案との違いを確認してから設定を用意する。取り込み時の待機短縮は人が記録し、cargo-denyの定期監査も併用する。GitHub Actionsを導入する場合はコミットへ固定する。

[依存監査](../.github/workflows/dependency-audit.yml)を毎日03:17 UTC（日本時間12:17）と手動で実行する。PRとmainへの変更は[Windows検証](../.github/workflows/windows.yml)内の`just verify`で同じ監査を行う。定期監査は読み取り権限だけで実行し、候補の製品コードをビルドしない。PRで変更された検査設定自身もレビュー対象であり、このジョブだけを悪意あるPRへの完全な防御とは扱わない。変更不能な外側の検査が必要なら、信頼した基点の設定を使う別の検査として設計する。

定期監査は依存を自動更新せず、公開・署名の手順とも分ける。全面的なcargo-vet導入と独自の依存解決器は採用しない。将来、Cargo標準の最低経過時間を採用する場合も、利用する安定版での対応と既存ロック依存の扱いを確認する。
